# ADR-025: Give the sandbox a mode per kind of course: SQL on its own database, a tryout generator, and a hub

- Status: built on 2026-10-16 at the owner's request ("sandbox mendukung apapun: sql maka playing sql, accounting maka playing accounting, utbk maka generate tryout", "ingat ini pakai docker aja", "tambahkan filtering dan infinite pagination scrolling di semuanya"); the limits and the scoring rule are proposals that wait for the owner (decision D-32)
- Date: 2026-10-16

## Context

The sandbox only knew accounting journals. A learner on the SQL course or on the UTBK course had nothing to practise with. Two things were needed that the existing practice API could not give: a place where learner-written SQL can run, and a way to produce many exam-style questions with a key that is certainly right.

The owner also ordered that everything runs in Docker, so SQL cannot run in the browser (a WebAssembly engine was set aside) and the API container must not run it either.

## Decision

1. **A hub at `/sandbox`.** It lists the three modes (accounting journals, SQL, tryout) and, for each course the learner follows, the mode that fits it: a course about UTBK, SNBT or SNPMB goes to the tryout; one about SQL or databases goes to the SQL playground; one about accounting goes to the journals; every other course falls back to practice inside the course (`/my-learning/topics/{slug}`). The match is by whole words in the slug and the title (`lib/playground.ts`), so "jurnalistik" or "sqlalchemy" do not match.
2. **SQL runs in its own PostgreSQL service, `sandbox-db`.** It has no published port, keeps its data in `tmpfs`, and is reachable only from `api` through `SANDBOX_DATABASE_URL`. It is not the application database; `api` stays the only service that touches the application database. The role `sandbox_runner` is not a superuser, has a connection limit, may create only inside its own database, cannot read `pg_stat_activity`, files or passwords, and carries role-level limits (statement timeout 2.5 s, lock timeout 1 s, temp file limit 32 MB, work memory 4 MB).
3. **A learner's SQL passes a guard before it is sent** (`sql-guard.ts`): comments are removed by a tokenizer that knows PostgreSQL strings, escape strings, quoted names and nested comments; dollar quoting and Unicode escaped names are refused; only SELECT, WITH, VALUES, TABLE, INSERT, UPDATE, DELETE, EXPLAIN and CREATE or DROP of tables, indexes and views, ALTER TABLE and TRUNCATE are allowed; and functions that read files, end sessions, change settings, take advisory locks, sleep, run a string as SQL (`query_to_xml`, `ts_stat`, `dblink`) or open system tables of passwords and sessions are refused. The guard is the only thing that stops `set_config`, because a role may set its own session settings; the role limits are the second wall for everything else, and the extended protocol (one statement per message) is a third that makes a smuggled second statement impossible.
4. **Every run starts from the same data and leaves nothing.** One transaction creates a schema with a random name, loads the dataset, runs the statements and always rolls back. A query is read through a cursor so a huge result is never produced; a statement that changes data returns at most 200 rows even with RETURNING; a run has 6 seconds in total, four runs may be active and eight may wait, and a watchdog ends a backend that outlives the budget. A learner is limited to 40 runs or checks per minute.
5. **A check compares results, not text.** The expected result comes from running the reference SQL on the same dataset once; numbers compare as numbers, rows compare as a multiset unless the task asks for an order, and a task that changes data or a table is judged by a fixed verification query run afterwards. The feedback says what differs (columns, rows, values, order) without showing the answer. A hint opens only after an attempt for each step, and the reference answer opens only after an attempt and does not count as solved. Progress is one row per learner and exercise (`SandboxSqlProgress`).
6. **A tryout is generated, not asked from a model.** Numeric and logic questions (series, syllogisms, conditional reasoning, rankings, percentages, ratios, algebra, geometry, probability, unit conversions, tables) come from seeded generators that compute the key from the same numbers as the question; verbal questions come from a bank written by hand (`tryout-utbk-bank.json`: vocabulary, idioms, affixes, standard spelling, effective sentences, paragraph ideas, two Indonesian and two English reading passages). The tests recompute every key a second way (search, enumeration, truth tables over the premises, every ordering of a ranking) over 40 seeds, and one of them found two options that were also true.
7. **A tryout session** keeps its questions and key on the server (`TryoutSession`), shows the questions without the key, saves answers as they are given, ends at the deadline plus 15 seconds of grace, and is graded under a row lock so a double submit gives one result. The time per question follows the official seconds (60, 45, 75, 60, 85, 60 and 127.5), so the TPS preset is 90 questions in 90 minutes. The score is the share of correct answers and is labelled as not the official IRT score. One session may run at a time (a partial unique index). A finished session writes one piece of learner evidence per concept with at least two questions, only when at least half of the questions were answered.
8. **Lists page and filter on the server where the data is.** The accounting catalog takes `limit` and `cursor`; a new `GET /sandbox/tryout/history` filters by score band and subtest and sorts. The web adds one footer component with an intersection observer and a button, a feed composable for server pages and an incremental composable for lists that are already in memory (SQL exercises, result rows, review items, the learner's courses).

## Consequences

- A new mode is a new playground entry and a new route; the hub and the course matching need no other change. A new exam would need its own bank and generators and its own plan schema.
- The questions in the reading subtests are few (11 and 10 against 30 and 20 in the real test), so the literacy preset is shorter than the real one and says so. More passages are content work, not code.
- `api` now depends on a second database. If `sandbox-db` is down the SQL pages show a notice and every other page works; the API answers 503 for a run.
- The disk of `sandbox-db` is a memory-backed 256 MB volume. A statement that writes a lot is stopped by the timeout and the temporary file limit, but the role has no disk quota. A restart of the container resets everything, which is the intended behaviour.
- The tryout history reads at most the 200 most recent finished sessions of a learner before it filters.
- Not done: SQL evidence for the learner model, rewards for solving an exercise, per-subtest timers with forced order, a second SQL dataset, a tryout for other exams, and an LLM that writes questions (it would need the judge of O-02).
